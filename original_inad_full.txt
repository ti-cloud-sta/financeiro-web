259: ### 2.3 O Coração: Parsers Determinísticos em Cascata
260: 
261: O método `extrair_beneficiarios_pdf_universal()` no `IAService` tenta **8 parsers em sequência**.
262: O primeiro que produzir resultado é usado. Nenhuma chamada à IA é feita nesse ponto.
263: 
264: ```python
265: formatos = [
266:     lambda: self._fmt_unimed_single_line(lines),       # Formato A
267:     lambda: self._fmt_matricula_suffix(lines),          # Formato E
268:     lambda: self._fmt_seguro_vida(lines),               # Formato B
269:     lambda: self._fmt_rubrica_multiline(page_texts),    # Formato A2
270:     lambda: self._fmt_coparticipacao(lines),            # Formato H
271:     lambda: self._fmt_responsavel(lines),               # Formato G
272:     lambda: self._fmt_sorriso_fragmented(lines),        # Formato F
273:     lambda: self._fmt_generic(lines),                   # Formato C (genérico)
274: ]
275: ```
276: 
277: #### Detalhe de cada parser:
278: 
279: **`_fmt_unimed_single_line` (Formato A):**
280: - Detecta: padrão de número de beneficiário `X.XXXXXXX.XXXXXXXX-X` (pelo menos 5 ocorrências)
281: - Cada linha contém: nome, matrícula, tipo `T/D/A`, valor, e eventualmente CPF
282: - CPF tentado em dois formatos: `000.000.000-00` (formatado) ou 8-11 dígitos consecutivos (sem pontuação)
283: - Agrupa por matrícula (prefix)
284: 
285: **`_fmt_matricula_suffix` (Formato E — Analítico de Taxa Unimed):**
286: - Detecta: linhas no padrão `prefixo.partes-sufixo NOME TIPO RUBRICA valor`
287: - Sufixo `00` = titular, demais sufixos = dependentes da mesma família
288: - **Nunca tem CPF** → marcado como `permite_fallback_nome = True`
289: 
290: **`_fmt_seguro_vida` (Formato B):**
291: - Detecta: marcadores `ALT/INC/EXC` colados a dígitos nas linhas (pelo menos 5)
292: - Padrão: `valor + matrícula + nome + tipo (T/D) + CPF`
293: - Se campo após T/D tem 10-11 dígitos, é o CPF
294: 
295: **`_fmt_rubrica_multiline` (Formato A2 — Demonstrativo Analítico Unimed):**
296: - Detecta: rubricas específicas (Mensalidade, Prêmio, Cobrança/Devolução Retroativa)
297: - Registro de beneficiário quebrado em múltiplas linhas
298: - Janela de busca: 200 chars antes da rubrica para encontrar nome + CPF
299: 
300: **`_fmt_coparticipacao` (Formato H — Co-participação / Analítico de Serviço):**
301: - Detecta: headers `NOME - MATRÍCULA + Matrícula` + linhas `TOTAL TITULAR`
302: - Usa o total já calculado no PDF, não soma individual por atendimento
303: - **Nunca tem CPF** → marcado como `permite_fallback_nome = True`
304: 
305: **`_fmt_responsavel` (Formato G):**
306: - Detecta: blocos `Responsavel: <cod>` + linhas `codigo NOME ... Valor Benef: valor`
307: - Titular identificado pelo código que bate com o `Responsavel:`
308: - Ordem dentro do bloco não é confiável (titular pode vir depois do dependente)
309: 
310: **`_fmt_sorriso_fragmented` (Formato F — Sorriso Odontológico via PyPDF):**
311: - Detecta: tipo `T` ou `D` isolado em sua própria linha (pelo menos 5 ocorrências)
312: - O PyPDF fragmenta as tabelas do Sorriso em uma célula por linha
313: - Nome: busca para trás a partir do índice do tipo; Valor: busca para frente
314: - CPF: busca sequência de 8-11 dígitos para frente
315: 
316: **`_fmt_generic` (Formato C — Genérico):**
317: - Detecta: padrão `NOME ... valor ... T/D` ou `valor ... NOME ... T/D` em uma linha
318: - Último recurso; menos preciso
319: - Skip de palavras reservadas: SUBTOTAL, TOTAL GERAL, PÁGINA, COMPETÊNCIA etc.

323: ### 2.4 Fallback para IA (Gemini) — Quando e Como
324: 
325: A IA é acionada **somente** em duas condições, após todos os parsers Python rodarem:
326: 
327: ```python
328: # Condição 1: Nenhum beneficiário extraído (PDF escaneado, layout completamente desconhecido)
329: if not titulares_list:
330:     motivo_fallback = "nenhum beneficiário extraído"
331: 
332: # Condição 2: Total calculado ≠ total impresso no documento (diferença > 1% ou R$ 1,00)
333: elif total_esperado is not None and abs(soma_calculada - total_esperado) > max(1.0, total_esperado * 0.01):
334:     motivo_fallback = f"calculado={soma_calculada} vs impresso={total_esperado}"
335: ```
336: 
337: O total impresso é detectado por `_detectar_total_esperado()` que procura âncoras:
338: - `TOT AL EMPRESA`, `TOTAL GERAL`, `TOTAL DA FATURA`, `VALOR TOTAL:`, `^Total.:`
339: 
340: Se a IA também falhar → resultado do Python é usado mesmo assim (melhor que nada).

358: ### 2.6 Resolução de Colaboradores — `_resolver_colaborador()`
359: 
360: Hierarquia rígida, sem ambiguidade:
361: 
362: ```
363: 1. CPF presente no PDF:
364:    → ColaboradorRepository.get_by_documento(cpf_normalizado_11_digitos)
365:    → Se encontrado: usa. Se não encontrado: FICA SEM VÍNCULO (não cai para nome!)
366: 
367: 2. CPF ausente → consulta tabela de aliases:
368:    → ColaboradorAliasRepository.get_by_nome_divergente(nome_pdf)
369:    → Se existe alias: usa o colaborador vinculado
370: 
371: 3. CPF ausente + formato sem CPF (unimed_matricula_sufixo ou coparticipacao):
372:    → permite_fallback_nome = True
373:    → ColaboradorRepository.get_by_nome_normalizado(nome_pdf)
374:    → Normalização: maiúsculas, remove acentos, sem espaço duplo — comparação EXATA
375: 
376: 4. Nenhum match: retorna None → usuário associa manualmente na tela de conferência
377: ```
378: 
379: **Normalização de CPF (`_normaliza_cpf`):**
380: - Remove todos os não-dígitos
381: - Se resultado tem 8-11 dígitos: completa com zeros à esquerda até 11
382: - CPFs abaixo de 8 dígitos: descartados (inválidos)
383: - Razão: alguns PDFs guardam CPF como número, perdendo zeros iniciais

388:

399:   → `alias_repo.create_or_update(colab.idColaborador, nome_pdf.strip())` é chamado
400: - Na próxima importação com o mesmo `nome_pdf`:
401:   → `alias_repo.get_by_nome_divergente(nome_pdf)` retorna o vínculo diretamente
402:   → Sem precisar de IA, sem interação manual

406: ### 2.8 Persistência na Confirmação (`confirmar_sorriso` / `confirmar_unimed_odonto`)
407: 
408: Fluxo idêntico nas duas rotas:
409: 
410: ```python
411: 1. _resolver_empresa_e_categoria(id_empresa):
412:    - Tenta empresa pelo ID
413:    - Fallback: empresa de nome "RDV - SANTA MARIA"
414:    - Fallback: primeira empresa do banco
415:    - Categoria: se "seguro" no nome da empresa → "Seguro/Saúde" (id=9)
416:               se não → "Plano de Saúde" (id=8)
417: 
418: 2. Cria Importacao(tipo="PLANO_SAUDE" ou "SEGURO")
419:    db.flush() → gera idImportacoes antes do commit
420: 
421: 3. Para cada titular:
422:    a. Resolve colaborador: primeiro por id_db (manual), depois por CPF normalizado
423:    b. Se não encontrado → adiciona em erros_colaboradores, continua (não cancela tudo!)
424:    c. Salva alias se nome_pdf != colaborador.nome
425:    d. Atualiza Centro de Custo do colaborador se foi modificado na tela
426:    e. (Apenas Unimed) Atualiza Unidade do colaborador se foi modificada na tela
427:    f. Cria Movimentacao(valor = titular.valor_total)
428:    g. Se payload.dataCompetencia: createdAt = datetime.strptime(dataCompetencia, "%Y-%m-%d")
429:       → DIFERENÇA CRÍTICA vs Despesas: aqui a data é a competência real, não a de importação!
430: 
431: 4. db.commit()
432: 5. Retorna {sucesso, idImportacoes, movimentacoes_criadas, erros_colaboradores}
433: ```
434: 
435: > ⚠️ **ATENÇÃO:** Colaboradores não encontrados são **ignorados silenciosamente** (com log
436: > no console). A importação prossegue parcialmente. Isso é intencional — diferente de
437: > Despesas que lança HTTP 400 e cancela tudo.

567: ## PARTE 6 — MÓDULO INADIMPLÊNCIA / PENDÊNCIAS
568: 
569: Este módulo controla as pendências e títulos em aberto importados.
570: 
571: ### 6.1 Regras de Negócio e Banco de Dados (Views)
572: - **NÃO MEXER NO SQL**: O agente é expressamente proibido de editar os arquivos `.sql` que contêm a view `vw_nfpendencias_fase` e afins. Qualquer alteração de lógica de fase (Financeiro, Logística, Pendências, etc.) deve ser instruída pelo agente para que o usuário copie a query e aplique no banco manualmente.
573: - **Fase PENDENCIAS**: Trata-se de uma fase de exceções e triagem. Regras documentadas rigorosamente no arquivo `.agents/rules/importar-pendencias-legacy-rules.md`. Exceções de importação caem aqui, como status `PR`, `RJ`, `DES`, `AD`, `AN`, `EXPORTACAO`, `MARTINS`, etc.
574: - **Padronização**: Status `Ok` foi substituído para `OK`. Status `CART-DES` foi simplificado para `DES`. Status `PR/RJ` foram desmembrados.
575: 
576: ### 6.2 Comportamento da Interface Kanban
577: - **Drag & Drop (FINALIZADO)**: Quando um card é removido manualmente da coluna "FINALIZADO" para outra fase (coluna), o frontend intercepta a ação e exibe o popup `pendencia-detalhe-modal`. O usuário deve obrigatoriamente selecionar um "Novo Status" neste modal antes de persistir o movimento.
578: - **Lista de Status (Filtro)**: O *select box* de filtro do Kanban no topo foi padronizado para usar a constante estática e alfabética `STATUS_OPTIONS` do `pendencia-detalhe-modal.component.ts`, garantindo que todas as opções estejam sempre visíveis independentemente dos cards filtrados em tela. O option "Todos" mapeia para o valor `"null"` (string).
579: 
580: ### 6.3 Toggles e Cores de Exceção (Aba Kanban)
581: A interface do Kanban possui *toggles* no cabeçalho das colunas para alternar a visibilidade de cards críticos:
582: - **Coluna Logística**: Possui um toggle laranja (`switch-orange`) para mostrar/ocultar os status de `DEVOLUCAO` (cor `orange`).
583: - **Coluna Financeiro**: Possui um toggle vermelho (`switch-danger`) para mostrar/ocultar os status de `PROTESTADO` (cor `danger`).
584: - **Atrasados**: Cards com status `ATRASADO` assumem a cor `warning` (laranja claro/amarelo escuro) para se destacarem.
585: - **Auto-Ativação**: O evento `onStatusFiltroChange` monitora o filtro global do Kanban. Ao selecionar explicitamente a opção "DEVOLUCAO" ou "PROTESTADO" no select, o sistema **liga** (true) automaticamente o *toggle* respectivo na coluna correspondente, permitindo que os cards se tornem visíveis.
586: 
587: ### 6.4 Regras de Importação de Planilha (InadimplenciaService)
588: - **Leitura Exclusiva da Aba Resumo**: O método `importar_pendencias` deve ler rigorosamente a aba denominada `Resumo` (`sheet_name="Resumo"`), ignorando e não verificando qualquer outra aba do arquivo.
589: - **Identificação e Chave de Unicidade**:
590:   - A pendência é identificada combinando `(idUnidade, serie, titulo, parcela, especie, carteira)` através do método `_obter_pendencia_existente`.
591:   - O mesmo número de título e parcela pode conter linhas diferentes com espécies distintas (ex: `DP` e `AD`) ou carteiras distintas. Essas linhas coexistem como registros autônomos no banco de dados, sem colisão ou sobrescrita mútua.
592: - **Atualizações em Reimportações**:
593:   - **Saldo (`valorSaldo`)**: Quando o saldo de uma pendência existente difere na nova planilha (ex: amortizações e pagamentos parciais), ele é atualizado imediatamente (independente de mudanças de vencimento) e gera o histórico de *"Atualização de Saldo"*.
594:   - **Carteira (`carteira`)**: Caso a carteira seja alterada (coluna M), o campo é atualizado, os campos manuais `fase` e `status` são limpos (`None`) para que a view `vw_nfpendencias_fase` reclassifique o título automaticamente, e são gerados os históricos de *"Atualização de Carteira"* e *"Classificação"*.
595:   - **Prorrogação de Vencimento**: Se a nova data de vencimento for maior que a anterior (`venc_excel > venc_db`), marca como prorrogado (`encerrado = 'P'`) e gera os históricos *"Título Prorrogado"* e *"Resolução"*.
596:   - **Ajustes de Vencimento**: Se a data for diferente sem prorrogação (`venc_excel != venc_db`), a data é atualizada com histórico cadastral.
597:   - **Status Reaberto**: Se uma pendência constava como `encerrado = 'S'` por ausência em importação prévia e retorna na planilha atual, seu status é revertido para `encerrado = 'N'`.
598: - **Rastreamento por ID e Baixa Automática por Ausência**:
599:   - O processamento acumula os IDs de banco (`idnfpendencias`) de todos os títulos processados em `ids_processados_planilha`.
600:   - Ao final do lote, todas as pendências ativas no banco (`encerrado = 'N'`) cujos IDs não estiverem no conjunto são marcadas como `encerrado = 'S'` gerando o histórico *"Pendência finalizada"*. Essa checagem por ID impede baixas indevidas cruzadas entre diferentes espécies do mesmo título.
601:
